# HarborWing Air — IT8 Midterm Drill

A MySQL 8.0+ relational database for fictional regional airline reservations. All passenger and operational records generated by the seed script are synthetic.

## Project files

- `sql/schema.sql` — creates the database and 11 core tables, keys, constraints, and indexes.
- `sql/example_queries.sql` — four required sample queries and row-count verification.
- `scripts/seed_data.py` — repeatable Faker-based data generator (fixed seed `20261016`).
- `requirements.txt` — Python dependencies.
- `docs/design-notes.md` — table purposes, relationships, assumptions, trade-offs, and video checklist.
- `docs/erd.mmd` — Mermaid ER diagram source. Import/recreate the schema in MySQL Workbench and save the native `.mwb` file plus an exported diagram PDF/image for submission.

## Requirements

- MySQL Server 8.0 or newer
- MySQL Workbench
- Python 3.10+
- Git (for GitHub submission)

## Setup

1. Open MySQL Workbench and connect to your local MySQL server.
2. Open `sql/schema.sql` and execute the entire script. **Warning:** it starts with `DROP DATABASE IF EXISTS harborwing_air`; remove that line if you must preserve an existing database with that name.
3. In a terminal at the project folder, install dependencies:

   ```bash
   python -m pip install -r requirements.txt
   ```

4. Configure the database connection. Defaults are host `localhost`, port `3306`, user `root`, blank password, and database `harborwing_air`. If your MySQL account has a password, set environment variables before running the script. In Windows PowerShell, for example:

   ```powershell
   $env:DB_USER="root"
   $env:DB_PASSWORD="your_mysql_password"
   python scripts/seed_data.py
   ```

5. Run `sql/example_queries.sql` in Workbench. Confirm every table has at least 50 rows. The calendar table has more than 1,000 rows because it contains each date from 2025 through 2027.

## Workbench EER diagram

After running `schema.sql`, choose **Database → Reverse Engineer**, select the `harborwing_air` schema, and finish the wizard. Arrange the tables so that `reservation` is central; put `passenger` and `booking_agent` to its left, `payment` and `flight_leg` to its right, the two linking tables between their parent pairs, and `flight_schedule`, `airport`, `flight_cost`, and `calendar_date` around the flight-related tables. Save as `HarborWing_Air.mwb` and export the diagram as PDF or PNG. The Mermaid source in `docs/erd.mmd` is a reference, not a substitute for the required native Workbench file.

## Assumptions

- `flight_number` is treated as a unique schedule identifier as instructed. A production airline may reuse a flight number on different dates, routes, operating carriers, or codeshare services, so it would usually need a separate schedule-instance ID and/or a composite identifier.
- Status, ticket, travel-class, airline, and aircraft codes are externally managed code values; no foreign keys are declared to nonexistent reference tables.
- Timestamps are stored in UTC.
- Deleting a passenger, airport, scheduled flight, or leg used by other records is restricted. Deleting an agent sets a reservation's `agent_id` to `NULL`. Deleting a reservation or payment deletes its link rows. Deleting a linked leg is restricted.

## Important limitations

- A shared payment link only says which reservations are connected to a payment. It does not state how much of that payment belongs to each reservation.
- `party_size` records the group size but not each traveler.
- Normalization reduces repeated passenger, airport, and flight information, but queries require joins.
- The schema validates cost date order but does not prevent overlapping validity ranges for the same flight and aircraft type. The application or a trigger/procedure should enforce a no-overlap policy if the business requires it.
